# 常规验证流程

本文件集中维护验证步骤，按本次改动选择必要检查；不默认执行完整玩法回归。

1. **确认范围。** 先确认改动入口、直接调用方和相关设计规则，确定预期行为及关键边界，再修改代码；按需读取文件，避免全库扫描。
2. **按风险选择检查。** 文档改动检查内容和链接；局部数值、样式或导入改动检查对应结果，影响浏览器模块加载时检查启动；模型改动检查实际外观、尺寸、碰撞范围及合批兼容性；碰撞、路线切换、状态和事件时序改动检查相关正常路径及关键边界。音效改动检查对应事件触发、暂停静音与新局恢复；`AudioContext` 依赖用户手势，浏览器验证需实际开始一局确认声音与控制台。
3. **检查代码与逻辑。** 修改 JavaScript 后对改动文件执行 `node --check`，交付前检查 diff。逻辑边界必要时用一次性 Node 脚本验证；核心逻辑重构必要时使用相同种子与输入对照新旧行为。不主动新增测试文件或引入构建步骤。
4. **确认实际表现。** 先按下文检查浏览器端口与服务；有 `cua_repl` 的会话优先使用该工具，其他环境可按下文选择轻量 Playwright 方案，并遵循各自的浏览器操作限制。同一批改动完成后统一刷新加载最新代码，检查实际画面、对应操作和控制台错误。自测勾选“调试模式”，避免写入排行榜；已有页面可能丢失用户进行中的游戏时使用临时标签，保留用户状态。
5. **补充必要边界与测量。** 涉及时钟、状态、缓存或对象池时，检查对应的暂停冻结与新局重置。性能优化先做小规模基线测量，比较时保持场景、车辆数量、种子、步数和计时范围一致；区分逻辑步与完整帧耗时，不将合成压力结果直接推算为普通游戏帧率。只有测量不足、出现失败或仍有边界疑点时扩大种子、运行时长及压力规模。
6. **结束并清理。** 必要检查通过且没有未解决疑点后结束验证；后续仅重验受新增修改影响的部分。关闭自行创建的临时标签和服务，清除临时调试入口，保留用户已有的页面、服务和工作内容。交付说明报告结果、有效证据及影响结论的验证缺口，不逐项列出常规检查通过情况。

## 浏览器端口与服务检查

预览前确认端口可达，且服务指向当前工作目录；默认使用 `5173`，占用时通过 `PORT` 指定空闲端口，不停止用户已有服务。

启动后确认成功日志和 HTTP 响应，再用当前环境允许的浏览器工具打开对应地址，刷新检查最新画面与控制台。连接失败先检查服务和端口，权限错误按工具流程处理，避免无依据地反复重试。

验证结束只关闭自行创建的临时标签和服务，保留用户已有页面与游戏状态。

## 轻量 Playwright 验证方案

默认采用一次性 Node 脚本验证受影响的逻辑，再集中做一次浏览器确认。已有 `cua_repl` 时无需额外安装；缺少浏览器工具且环境允许时，可选择以下方案：

- 在仓库之外的通用工具目录（如 `/Users/allan/dev-tools/browser-check`）安装 `playwright-core`，固定版本并维护该目录自己的 `package.json` 和锁文件；不全局安装，不改各项目依赖，也不引入完整测试框架。通用验证脚本放在工具目录并从该目录执行，各项目传入 URL、端口及输出路径，跨项目复用。
- 本方案浏览器固定使用已安装的 Google Chrome，通过 `chromium.launch({channel:'chrome',headless:false})` 启动独立验证浏览器；这里的 `chromium` 是 Playwright API 名，`channel:'chrome'` 指定实际使用 Chrome，无需执行 `playwright install`。环境没有 Chrome 时先披露缺口，不自动安装浏览器。此方式复用浏览器程序，不复用用户正在使用的进程或个人资料。[浏览器配置官方说明](https://playwright.dev/docs/browsers)
- 每次验证使用独立浏览器上下文及临时产物目录，避免项目之间状态混用；只使用一个浏览器和一个页面，打开已确认的本机 HTTP 地址，启用游戏调试模式，检查当前改动涉及的操作、画面和控制台。音效验证需通过实际点击或按键开始游戏并试听，不能仅凭截图或控制台认定声音正常。
- 不默认开启并行、录像或完整追踪，截图按需保留；用 `try/finally` 关闭本次启动的浏览器和服务，只清理本次临时产物，长期保留通用工具目录及其他项目输出。共享目录减少重复安装与磁盘占用；实际内存主要来自浏览器与游戏场景，具体占用与速度收益需实测。

固定种子和直接进入目标场景是独立的开发入口方案，`cua_repl`、手动浏览器或 Playwright 均可使用；目前属于待验证建议，不能通过只改时钟跳过事件逻辑，仍需验证触发前后的边界。

## URL 测试参数(随机事件快速触发)

随机事件(警车、白马、奶牛、施工、低速车队、天气、断头路、天降炮击)默认节奏为分钟级,浏览器验证时通过 URL 查询参数在启动早期覆盖 `config.js` 白名单字段,不改代码、不落存档；移除 URL 参数后刷新恢复默认;生产环境不带参数即默认值。

- `?fast=1`:一键测试档,主要随机事件压缩到秒级(警车 3–8 秒、数学/语文/英语答题均为 5 秒、白马每 8 秒、奶牛 4–8 秒、施工从道路 10 米处开始候选、低速车队 3 秒首现、天气 2–4 秒首现后每 6–10 秒、分叉候选概率为 100%、建筑间距压缩到 500–800 米；分叉仍受最小跨度与可用空间限制，不保证生成、炮弹 8 秒开始且每 3–5 秒一发，15 秒后每 1.5–2.5 秒一发，下落 1.5 秒；独立 X 路障 15 秒后启用，每 240 米检查且候选概率为 100%，仍避开施工、道路过渡和桥梁分叉)。
- 精确覆盖:`?POLICE.intervalMin=3&POLICE.intervalMax=8&WHITE_HORSE.intervalSeconds=5&WEATHER.intervalMin=6&ROAD_FORKS.chance=1&SHELL.intervalMin=3`,只接受白名单配置字段（含警车距离、倍率与网尺寸，不含车型尺寸与车辆碰撞阈值）,答题时限可用 `POLICE.quizMathSeconds`、`POLICE.quizChineseSeconds`、`POLICE.quizEnglishSeconds` 单独覆盖；非法 key 或非数值直接忽略并控制台告警,防止误改物理与碰撞参数。
- 覆盖生效时页面右上角显示测试参数角标,截图即可确认当前处于测试节奏,避免把测试结果当默认行为;`?fast=0` 关闭预设。
- 验证火车或其他环境事件时可用 `?TRAFFIC_DENSITY.capacity=0&TRAFFIC_DENSITY.maxCapacity=0` 清空普通车流；两个容量同时为零可避免运行中容量增长后重新补车。需要少量车流时将两者设为相同的小整数，例如 `6`；也可单独覆盖 `TRAFFIC_DENSITY.capacityPerStep` 调整增长量。不带这些参数即恢复正常车流，不写入存档。

实现见 `src/test-overrides.js`,由 `config.js` 末尾在启动早期应用;Node 端导入无 `location` 自动跳过。独立 X 路障可用 `ROADBLOCKS.afterSeconds`、`first`、`interval`、`chance`、`warningDistance` 覆盖启用及候选节奏；炮击加密阶段可用 `SHELL.frequencyAfterSeconds`、`lateIntervalMin`、`lateIntervalMax` 覆盖。新增随机事件时在 `WHITELIST` 登记节奏字段,并按需加入 `FAST_PRESET`。

流程的效率改进与待验证建议见[开发与验证效率](development-workflow.md)，其中推测意见不作为默认执行要求。
