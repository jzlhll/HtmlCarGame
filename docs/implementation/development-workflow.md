# 开发与验证效率

## 第一部分：目的与目标

本文用于减少开发过程中的重复核对、过度验证和无效工具往返，在保证改动正确性的前提下缩短交付时间，并让耗时原因和验证结论更清楚。

操作步骤统一见[常规验证流程](validation.md)，本文只维护效率改进依据与待验证建议；相关专题见[文档总览](../README.md)。

第二部分列出已有明确依据、可直接采用的改进；第三部分保留尚需实际验证的建议，不作为默认执行要求。

## 第二部分：目前明确的改进

1. **验证投入与风险匹配。** 核心碰撞、路线和事件时序存在交叉影响，需要较完整的核对；局部改动采用针对性检查，可减少无关回归。验证范围以独立的流程文档为准，不在多处重复维护。
2. **减少重复读取和工具往返。** 独立查询批量执行，依赖查询按结论顺序展开；已取得且仍有效的信息直接复用。只有新增修改、失败或未解决疑点才触发进一步检查。
3. **尽早用测量决定性能方案。** 调用频繁不等于成本高，算法复杂度也不等于实际收益。先用小样本确认热点和候选方案，未测出收益的优化不默认落地，正确性修复与容量保护按各自依据处理。
4. **合并浏览器验证。** 浏览器验证包含启动、刷新和工具等待成本，同一批修改集中预览可减少重复往返；脚本适合先定位逻辑边界，浏览器负责确认实际表现。服务或标签故障先定位原因，避免无依据地重复操作。
5. **让耗时与结论清楚。** 较长任务说明当前是在修改、核对边界、测量还是等待工具，以及下一步要解决的疑点。进度报告新结论，交付说明证据的适用范围；必要检查完成后结束验证。
6. **音效调参走配置与既有合成方式。** 新增声音优先复用 `audio.js` 既有的 `tone`/`burst` 与循环声模式拼装，数值进 `config.js` 的 `AUDIO`，刷新页面即可对比试听；环境声（火车、坦克、横风、河道）依赖场景自然触发，验证时可临时放宽触发条件复现，结束后还原，避免长时间等待。

## 第三部分：推测的改进意见

1. **复用少量典型验证场景。** 若重复出现相同的路线、碰撞和天气边界，可以探索复用固定种子与场景参数，减少每次重新组织验证的时间。需确认其覆盖范围和维护成本；不因此主动新增持久测试文件或调试入口。
2. **记录主要环节的耗时。** 可以在少量任务中记录代码核对、修改、脚本验证和浏览器验证的耗时，用数据决定下一步优化重点。需先确认记录成本足够低，不能仅凭主观感受设定统一时间上限。
3. **采用逐步扩大的验证样本。** 可以探索从少量有代表性的种子开始，发现差异后再扩大样本。需确认小样本能覆盖对应规则，碰撞和时序边界不能只靠随机样本判断。
4. **先确认模型造型，再细化渲染实现。** 可以探索先用轻量预览确认轮廓、尺寸和可见性，再完善材质、动画及合批。需验证是否确实减少返工，并计入额外预览与临时模型的成本。

如果发现实际有用有效的方式回落到第二部分，相关的推测部分进行调整。
